## P0-1 text 回调 `args[0].agent` 取不到 agent —— MEMORY 永不注入、/user 多魂实际失效

- **位置**：lib/workspace.js `registerAll()` 内 PERSONA_FILES / CONTEXT_FILES 的 `text` 回调（daily notes 与 inject 自由块的回调不取 agent，不涉及）
- **现状代码**：

  ```js
  text: function (args) {
    const agent = args && args[0] && args[0].agent
  ```

- **根因**：dsh 0.2.0-rc.2 官方对 section/context 的 text 回调是**单参数**调用 `text(context)`，`context = { agent, scope }` **普通对象**（真实请求来自 `dsh-agent` 的 `assembleContextFor(agent)`，返回 `{ agent, scope }`；全局预览时是 `{}`）。`args[0]` 恒为 `undefined`，agent 永远取不到。全生态只有 dsh-system-prompt 一处调用该回调（`section.text(context)` / `entry.text(context)`），不存在其他包装路径
- **证据**（真实包探针，2026-10-11）：用本机 `@deepseek-ai/dsh-system-prompt` + cordis Context 注册 section/context 后分别跑 `sp.assemble({})` 与 `sp.assemble({ agent, scope })`，实测回调 `argc = 1`、`arg0` 为**非数组对象**且含 `agent` / `scope` 键。探针脚本见文末附录
- **影响面**：
  1. **MEMORY.md 永不注入**——mainOnly 分支 `if (!agent) return ""` 直接拦截，真实会话中 context 段始终为空
  2. **/user 会话级多魂失效**——`serveTrioPiece(f, undefined)` 永远走根目录；绑定表能写进去（命令与面板都正常）但注入侧永远不读库存，§2.6 的 D9/D10/D11 实际不可用
  3. HEARTBEAT / daily notes / inject 自由块不取 agent，不受影响
- **为什么冒烟与日常使用都没发现**：
  1. §2.1「机制实测结论（M1 探针，2026-10-03）」把回调形状误判为数组（`args[0] = {agent}`），冒烟 mock 沿用了这个错误形状，测试集体失明——mock 与真实 API 脱节时测试没有拦截力
  2. 面板预览对 MEMORY 段做 RAW_VIEW 文件原文兜底（routes.js `buildPreview`），预览里「看着注入了」，实际为空——预览掩盖了真相
- **连带需要同步修正的文档记录**：docs/02 §2.1 注入总表 MEMORY 行（"text 回调读 `args[0].agent` 判定"）、§2.1「机制实测结论」、§2.6「注入改道」——三处均基于错误探针结论
- **修复建议**：

  ```js
  text: function (ctx) {
    const agent = ctx && ctx.agent
    ...
  ```

  同时把真实包探针固化进 tests/ 防复发
- **状态**：✅ 已修复（a1b148b）——workspace.js 两处回调改 `text(ctx)` 取 `ctx.agent`，头注释与 isMainSession JSDoc 同步；docs/02 §2.1 注入总表 MEMORY 行、§2.1 机制实测结论、§2.6 注入改道三处文档记录一并修正；探针固化于 `tests/probe-text-callback.mjs`（断言式，形状漂移退出码 1）

## P2-1 读子代理输出使用了官方已 @deprecated 的 snapshotEvents

- **位置**：lib/autowrite.js `readChildOutput`
- **说明**：dsh-session 0.2.0-rc.2 将 `snapshotEvents` / `eventAt` 标注 @deprecated（"new calls are prohibited"，建议读官方 Agent Note）。官方 agent-loop 自身也还在用（存量未迁移），所以非硬伤、不算错误
- **改进建议**：`@deepseek-ai/dsh-subagent` 提供了官方 `finalAssistantOutput(events)`，语义即「选子代理最后一条非空 assistant 消息」，还处理了空消息与流式 fallback 边界——可替换手写的等价逻辑
- **状态**：⏸ 暂不修。已实测官方包确实导出 `finalAssistantOutput`，但替换需要插件**硬 import** `@deepseek-ai/dsh-subagent`——本插件现有模式是零官方包依赖（agents/commands 等全部经 ctx 服务动态取，autowrite.js 头注释明言「零新增 npm 依赖」），插件目录无 node_modules 时硬 import 的解析路径不可控，风险大于收益；且官方 agent-loop 自身仍在用 snapshotEvents（非硬伤）。等官方完成迁移、或确认插件加载器的模块解析策略后再跟随

## E-1（修复中新增发现）HEARTBEAT seed 说明行导致新装门控失效

- **位置**：lib/workspace.js `SEEDS["HEARTBEAT.md"]`（2026-10-11 修复时发现，原清单未列）
- **说明**：seed 文案 `> 有实际任务时才注入…` 是 `>` 引用行，`heartbeatHasRealTasks` 只过滤空行 / `<!--` 注释 / `#` 标题，引用行被当作实际任务 → 新装用户 HEARTBEAT.md 一创建就满足注入条件，「有任务才注入」的门控直接失效，每轮请求多注入一段无用文案
- **修复**：seed 说明行改写为单行 HTML 注释 `<!-- … -->`（注释行被门控过滤，删掉注释写任务即正常注入）。只建不覆盖，既有用户的文件不受影响
- **状态**：✅ 已修复（2728c7a，已实测三种内容形态的门控判定）

## ✅ 验证通过的部分（自动记忆新功能本体）

自动记忆链路（autowrite.js）用到的每个 dsh API 都对照 0.2.0-rc.2 类型定义核过，**全部真实存在且签名正确**：

| API | 核验结论 |
|---|---|
| `ctx.on("session/event", cb, { global: true })` | 事件存在于 dsh-session；`global` 选项官方语义 = "Receive the event regardless of context filter checks"，正确 |
| `ctx.on("session/disposed", cb, { global: true })` | 事件存在且签名一致 |
| 回调形状 `(session, event)` | 与官方 dsh-compaction-basic 的监听写法一致 |
| `agents.create({ sessionId, meta, agentOptions, setup })` | AgentRegistry.create 完全一致；meta 的 cwd/parentSession/origin/delegationDepth/isSeeded 全是合法字段 |
| `agentOptions.subagentDepth: 1` | dsh-subagent 官方扩展字段（module augmentation），子代理深度 1 正确 |
| `setup` 内 `tools.restrict({ allow: [] })` | ToolRestriction.allow 官方语义正确，agent-scoped 生效 |
| `agentDefaultModel.currentSelection()` → `{ provider, model }` | ModelSelection 字段一致 |
| `session.requestHeader().config` | EpochHeader.config 存在 |
| `session.seq` / `followup` / `whenIdle` / `AgentHandle{ agent, dispose }` | 全部存在且用法正确 |
| `user/message`（data = UserMessage）、`assistant/message`（data.message）、`turn/end`（data.reason.kind） | 事件形状全部对得上；`source.kind === "runtime-context"` 过滤是官方 MessageSourceMap 扩展，过滤正确 |
| 主会话判定 `!header.parentSession && delegationDepth 0/undefined` | 字段全部真实存在；header 不可达时保守跳过（宁可少采集不误提子代理），与注入侧的保守方向（宁可多注入）各自合理 |

逻辑推演也自洽：防抖单飞（rearm）、快照消费、3 次失败丢弃、setConfig 差异键落盘（面板改回默认值会清掉文件键，行为正确）、与 fs.watch 热加载的配合。client 半的 `settings.section` 注册形状与官方 cookbook（slots.inject + slots.register list 槽）一致。

**结论**：自动记忆功能是真的实现了、API 用法挑不出毛病；P0-1 是它顺带掀出来的旧代码问题。
